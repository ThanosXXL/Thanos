# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Dozenten Dashboard is a cross-platform Electron desktop app for managing up to four *Dozenten* (instructors). Each instructor owns three lists — a To-Do list (`todos`), open projects (`openProjects`), and completed projects (`doneProjects`) — plus a chat/notes log (`chat`). Projects move between the open and completed lists; all state persists locally as JSON. The UI is in German.

This repository also hosts a second, unrelated project: `omniroute/` is a vendored snapshot of [OmniRoute](https://github.com/diegosouzapw/OmniRoute) (an AI gateway/router, Next.js + TypeScript monorepo), included as-is with its own `package.json`, tooling, and `CLAUDE.md`. It does not share dependencies, build config, or CI with the Dozenten Dashboard — the root `npm install`/`npm start`/`npm run dist` commands above only ever touch the Dozenten Dashboard files (`main.js`, `preload.js`, `renderer/`); nothing in `omniroute/` is packaged into its installers. Treat `omniroute/` as its own project — see `omniroute/CLAUDE.md` and `omniroute/VENDORED.md` for details and provenance. It is a one-time snapshot, not a live sync with upstream.

A third project, `it-schulung/`, is a separate Electron desktop app for managing up to four IT-Schulungen (IT training courses), built with the same architecture as the Dozenten Dashboard (main/preload/renderer split, `contextIsolation: true`, JSON persistence in `app.getPath('userData')`) but as fully independent code: its own `package.json`, `main.js`, `preload.js`, `renderer/`, and data file (`it-schulung-data.json`, separate from `dozenten-data.json`). Each *Schulung* object is `{ id, name, erklaerung, admin, link, todos, offeneThemen, abgeschlosseneThemen, teilnehmer, chat }` — the training-course equivalent of a *Dozent*. `erklaerung` is a free-text description, `admin` names the person responsible, and `link` is the join URL for the daily live session (opened via `shell.openExternal` through an `open-external` IPC handler, restricted to `http(s)` URLs). `teilnehmer` is a fourth list (alongside `todos`, `offeneThemen`, `abgeschlosseneThemen`) holding the course's participants as `{ id, text }` entries. Run it with `npm install` / `npm start` / `npm run dist` from inside `it-schulung/`, not from the repo root. It shares no dependencies, build config, or CI with the Dozenten Dashboard or with `omniroute/`.

A fourth project, `fotonetz/`, is a separate Electron desktop app ("FotoNetz") for managing up to six photography *Aufträge* (jobs/shoots), again built with the same main/preload/renderer architecture (`contextIsolation: true`, JSON persistence in `app.getPath('userData')`) as fully independent code: its own `package.json`, `main.js`, `preload.js`, `renderer/`, and data file (`fotonetz-data.json`). Each *Auftrag* object is `{ id, titel, art, kunde, termin, link, preis, zahlungsstatus, notizen, todos, offeneEdits, fertigeEdits, referenzen, chat }` — the photography-job equivalent of a *Dozent*. `art` is the job category, a fixed dropdown (`AUFTRAGSARTEN` in `renderer.js`: Hochzeit, Verlobung / Paarshooting, Taufe, Portrait, Familie, Business / Corporate, Werbung, Event, Produkt, Sonstiges) also shown as a badge next to the panel title. `kunde` is the client name, `termin` is a free-text date/location field, `preis` is a free-text fee/honorarium field, `zahlungsstatus` is a fixed dropdown (`ZAHLUNGSSTATUS`: offen/angezahlt/bezahlt, color-coded), `notizen` is a free-text description (equipment, client wishes, style), and `link` is the gallery/delivery URL (opened via `shell.openExternal` through an `open-external` IPC handler, restricted to `http(s)` URLs). The four lists are `todos`, `offeneEdits` (open editing/deliverable tasks), `fertigeEdits` (finished ones, movable back and forth like the other apps' open/done lists), and `referenzen` (reference/inspiration entries). The renderer bundles its own Poppins webfonts (`renderer/fonts/*.woff2`, fetched once from Google Fonts and vendored — no runtime network dependency) and uses a black/navy glossy visual theme with an animated 3D-style SVG camera logo; both are purely `renderer/style.css` + `renderer/index.html` presentation and don't affect the state/IPC architecture. Run it with `npm install` / `npm start` / `npm run dist` from inside `fotonetz/`, not from the repo root. It shares no dependencies, build config, or CI with the Dozenten Dashboard, `it-schulung/`, or `omniroute/`.

`fotonetz/` also has a media pipeline for per-*Auftrag* photo editing and slideshow-video creation, the one place in this repo that breaks the "no build step, no extra runtime deps" pattern: it depends on `ffmpeg-static` (a bundled ffmpeg binary, `dependencies` not `devDependencies`, unpacked from asar via `build.asarUnpack` in `package.json` since a binary can't execute from inside an asar archive) and on Electron's `dialog` API for native file pickers. Each *Auftrag* additionally carries `medien: { bilder: [], musikStueck: null | {...}, videos: [] }`. Imported/edited images and picked music are always copied (never referenced in place) into `app.getPath('userData')/fotonetz-media/<auftragId>/{originale,bearbeitet,musik,videos}/`; every media IPC handler in `main.js` (`import-images`, `pick-music`, `save-edited-image`, `create-slideshow-video`, `open-media-path`, `reveal-media-path`, `delete-media-file`) validates paths with `isInsideMediaRoot()` before touching the filesystem, mirroring the `http(s)`-only check on `open-external`. Each media entry is `{ id, dateiname, pfad, url }` (`pfad` is the real filesystem path used for IPC calls; `url` is a precomputed `file://` URL, built in the main process via `pathToFileURL`, for direct use in `<img src>` — the renderer never does its own path-to-URL string building). Image editing (`renderer.js`: `openImageEditor`/`drawEditorCanvas`/`saveEditedImage`, markup in the `#imageEditorModal` in `index.html`) is a `<canvas>` with `ctx.filter` for brightness/contrast/saturation plus 90°-step rotation; "save" exports `canvas.toDataURL('image/jpeg', ...)` to the `save-edited-image` handler, which writes it as a new `bearbeitet` entry (the original is never overwritten). Slideshow video creation (`generateVideo` in `renderer.js` → `create-slideshow-video` in `main.js`) picks images the user checked via a module-level `videoSelection` Set (UI-only, not persisted), spawns `ffmpeg-static` once to scale/pad/loop each selected image to a fixed 1280×720 slide and cross-fades consecutive slides into each other with ffmpeg's `xfade` filter (transition length `slideshowTransitionDuration()` = `min(1, secondsPerImage / 2)`, chained with cumulative `offset`s per the standard ffmpeg xfade recipe — see `buildSlideshowArgs()`), then — if a `musikStueck` is set — muxes and loops/trims the audio to match the video's exact length with `-shortest` (a second `ffmpeg` pass); with no music it just renames the silent render. Because the cross-fades overlap, the rendered video is shorter than `imageCount * secondsPerImage`; the actual duration (`slideshowTotalDuration()`) is computed analytically rather than assumed. Videos can also be imported directly (no re-encoding) via `import-videos`/`importVideos`, landing in the same `medien.videos` list with `quelle: 'importiert'` instead of `'erstellt'`. The media grid in `buildMedienPanel()` renders images and videos together in one gallery (an `<img>` or a `<video controls>` per card) rather than as two separate sections. There is still no test suite; the manual verification pattern for this feature is to stub `dialog.showOpenDialog` in a throwaway driver script before `require`-ing the real `main.js`, so the genuine shipped `main.js`/`preload.js`/`renderer.js` run under Electron with only the native file-picker swapped out.

Text meta-fields (`kunde`, `termin`, `link`, `preis`, `notizen`) save on blur *and* via an explicit "💾 Speichern" button built by `buildSaveButton(key, onSave)`; clicking it flips to a "✓" for about a second. Because every mutation re-renders the whole panel (see "State and data flow" above), that visual "saved" state can't just be toggled on the clicked DOM node — it would be wiped by the immediate re-render. It's tracked instead as a short-lived module-level `justSavedKey` (keyed `"<auftragId>:<field>"`, cleared by `flagJustSaved()`'s own timeout) that `buildSaveButton()` checks when constructing each button, so the freshly re-rendered button already shows "✓". Follow this pattern (flag-before-mutate, read-the-flag-when-rendering) for any future "flash an ephemeral state after an action that re-renders" UI, rather than mutating a button already in flight.

A fifth project, `pharma-tech-prototype/`, is a static HTML/CSS/vanilla-JS design prototype for Pharma-Tech ("Apotheken-Betriebssystem") — `index.html` is the full demo UI (Dashboard, Warenwirtschaft, Kasse, Kunden & Rezepte, Kundenkarte, Bestellungen, Botendienst, Analysen, Team & Notizen, Datenübernahme, Warum Pharma-Tech, Einstellungen) with fake in-memory data and no backend/IPC of any kind, plus marketing collateral (`flyer.html`/`flyer-3d.html`, `factsheet.html`, `manual.html`, `instagram-reel.html`, `instagram-vorteile.html`, `video-intro.html`/`video-outro.html`/`video-live.html`) and their rendered exports under `export/`. It is not an installable app by itself.

Each `video-*.html`/`instagram-*.html` marketing source is a standalone, self-contained scene: Baloo 2/Manrope are embedded directly as base64 `@font-face` `src` data (not loaded over the network, consistent with offline rendering via Playwright), and any embedded screen-recording clip (e.g. `video-live.html`'s device-frame insert, reused from the Instagram "Vorteile" reel) is likewise inlined as a base64 `data:video/webm;...` source rather than a sibling file — `video/webm` (not `.mp4`) specifically, because the headless Chromium used to render these pages for recording lacks H.264 decoding, so an embedded clip must be VP8/VP9 to actually play during capture; the final exported deliverable is still encoded to H.264 `.mp4` for playback compatibility everywhere else. These scenes are rendered to video by recording them with Playwright (`recordVideo`) and chaining the resulting clips with ffmpeg's `xfade` filter, the same pipeline used for all the video exports under `export/`.

The **Kundenkarte** view (`data-view="kundenkarte"`) is an optional, toggleable loyalty/bonus-points module ("auf Wunsch aktivierbar", mirroring the existing-but-inert `Kundenbindungsprogramm` entry in the `INTEGRATIONS` array): each `CUSTOMERS` entry carries a `punkte` field, `LOYALTY_TIERS` (`Bronze`/`Silber`/`Gold`, each with a point threshold and a benefit description) maps points to a tier via `loyaltyTierFor()`, and `renderLoyaltyCard()` draws a glossy gold 3D "membership card" (`.loyalty-card`, same layered-`box-shadow` glossy treatment as the rest of the app, with its own fixed gold gradient rather than the mint theme vars, since it represents a physical card) for the currently active customer. The module-level `loyaltyEnabled` flag, toggled by the `#loyaltyToggle` button, shows/hides the whole feature (`#loyaltyContent` vs. a `#loyaltyDisabledNote` banner) to make the "apotheke opts in or out" framing concrete rather than just a settings-page switch with no visible effect.

The **Datenübernahme** (migration) view's copy and `mig-stat`/`mig-check` rows explicitly call out that **Sortiment/Artikelstamm** and **Kontaktdaten** (not just Rezepte and Kassenhistorie) are transferred fully automatically and without loss, alongside the existing customer/prescription/order migration stats — keep new migration-related fields documented there the same way if the data model grows further.

The **Botendienst** customer-delivery list is a small state machine, not just a static badge: `offen → geplant` (via the existing date/time scheduler) `→ unterwegs → zugestellt`, each transition a live button in `renderCustomerDeliveries()` (`Unterwegs melden`, `Als zugestellt markieren`) that mutates `d.status` directly and re-renders, same pattern as the scheduler.

**Mitarbeiter-PIN-Login**: a full-screen `#loginOverlay` PIN keypad gates the app on load (`STAFF` array: `{ id, name, role, avatar, pin, pinSource }`, `pinSource` is `'it-world'` when IT-World provisioned it at setup or `'vor-ort'` once the pharmacy's own team has changed it locally — set automatically whenever the Einstellungen → "Mitarbeiter-PIN & Anmeldung" card's "PIN ändern" flow is used, so the two provisioning paths the business actually offers are visible in the UI, not just a one-time default). A correct 4-digit PIN hides the overlay and calls `setLoggedInStaff()`, which drives every other "who's logged in" surface (sidebar `user-chip`, topbar avatar, the dashboard's `Guten Morgen, …` greeting) from that one STAFF record — add any future per-staff display to that function rather than hardcoding a name elsewhere. Clicking the sidebar `user-chip` re-opens the overlay (logout).

**Angebot (customer quote)**: in the Kunden & Rezepte customer-detail panel, staff build a line-item quote per customer (`ANGEBOTE[customerId]`, in-memory only) and hand it to the customer via a native-browser print flow — `printAngebot()` fills the hidden `#angebotPrintView` with a clean letterhead/table layout and calls `window.print()`; a `@media print` block hides everything else via `visibility:hidden` so only that element prints (to paper or "Save as PDF" in the browser's print dialog). This keeps the no-dependency, no-backend constraint of the prototype intact rather than adding a PDF-generation library.

The **Botendienst** view (`data-view="botendienst"`) is a deliberate competitive differentiator, not present in typical pharmacy-management software: it combines (a) incoming supplier orders shown with an exact arrival date *and time* (`INCOMING_DELIVERIES`, each `{ id, supplier, items, status: 'bestellt'|'unterwegs'|'angekommen', date, time }`, rendered by `renderIncomingDeliveries()`), and (b) a staff-facing customer-delivery scheduler (`CUSTOMER_DELIVERIES`, each `{ id, kunde, adresse, artikel, status: 'offen'|'geplant'|'unterwegs'|'zugestellt', date, time }`, rendered by `renderCustomerDeliveries()`) where clicking "Termin festlegen" reveals inline `<input type="date">`/`<input type="time">` fields; confirming mutates the array entry directly and re-renders, the same direct-mutate-then-rerender pattern already used by `autoOrderBtn`. Because the whole view re-renders on every click, which row (if any) is mid-edit is tracked in the module-level `schedulingDeliveryId` variable rather than on the DOM node itself — the same "track transient UI state in a module variable, read it when rendering" pattern documented below for `fotonetz`'s save buttons. All icons are inline stroke-SVG (`ICONS.truck`, `ICONS.pin`) to stay within the page's CSP (no external images).

A sixth project, `pharmatech-app/`, is the Electron desktop wrapper around that same prototype — same architecture pattern as the Dozenten Dashboard (`contextIsolation: true`, `nodeIntegration: false`, plus explicit `sandbox: true`) but radically simpler, since the prototype needs no persistence or native capability: `main.js` just opens a `BrowserWindow` and loads `renderer/index.html` (a copy of `pharma-tech-prototype/index.html`, kept in sync manually — there is no build step or symlink tying them together), and `preload.js` intentionally exposes no API. `main.js` also routes any attempted navigation away from that bundled file (window-open, `will-navigate`) to the OS's default browser instead of loading it in-app. Run it with `npm install` / `npm start` / `npm run dist` from inside `pharmatech-app/`, not from the repo root. It shares no dependencies, build config, or CI with any other project in this repo.

The shared `index.html` (`pharma-tech-prototype/index.html` and its two synced copies) carries a restrictive `Content-Security-Policy` meta tag (`default-src 'none'` plus only the specific sources the single-file app actually needs: inline script/style, data: fonts/images). Keep it in sync across all three copies along with the HTML itself whenever either changes.

`pharma-tech-prototype/download.html` also has `impressum.html` and `datenschutz.html` siblings (Impressumspflicht under German TMG/DDG applies to any commercially-operated site, even a plain download page) — both contain placeholder business data in square brackets that must be replaced with IT-World's real details before the page goes live publicly.

A seventh project, `pharmatech-mobile/`, is the Android/iOS counterpart to `pharmatech-app/`. Since Pharma-Tech is pure demo UI with fake data and no native capability requirements, `pharmatech-mobile` takes the pragmatic route instead of a native rebuild: it bundles the identical prototype (`assets/www/index.html`, also a manually-kept-in-sync copy of `pharma-tech-prototype/index.html`) and renders it inside a single `react-native-webview` view (`App.tsx`). `metro.config.js` adds `html` to `resolver.assetExts` so `require('./assets/www/index.html')` bundles as an asset; `App.tsx` resolves it at runtime via `Asset.fromModule(...).downloadAsync()` and hands the WebView the resulting local URI. Because it has no native modules beyond the Expo-Go-compatible `react-native-webview`, it needs no Expo config plugin and runs directly in Expo Go, no dev client required. Run it with `npm install` / `npx expo start` (Expo Go) or `eas build -p android --profile preview` (real APK) from inside `pharmatech-mobile/`, not from the repo root. It shares no dependencies, build config, or CI with any other project in this repo.

## Commands

```bash
npm install     # install dependencies
npm start        # run the app in development (electron .)
npm run dist     # build installers into dist/ via electron-builder (win: nsis, mac: dmg, linux: AppImage)
```

There is no test suite, linter, or build/transpile step — the renderer is plain HTML/CSS/vanilla JS loaded directly, and the main process is plain Node. Changes are verified by running `npm start`.

## Architecture

Standard Electron three-process split with `contextIsolation: true` and `nodeIntegration: false`:

- **`main.js`** (main process) — creates the `BrowserWindow`, and owns all persistence. Registers two IPC handlers, `load-data` and `save-data`, that read/write a single JSON file at `app.getPath('userData')/dozenten-data.json`. `loadData()` returns `{ dozenten: [] }` on any read/parse failure, so a missing or corrupt file degrades gracefully.
- **`preload.js`** — the only bridge. Exposes `window.dashboardAPI` with `loadData()` and `saveData(data)`, each forwarding to `ipcRenderer.invoke`. Any new main↔renderer capability must be added here; the renderer has no direct Node/Electron access.
- **`renderer/`** — the entire UI. `index.html` is the static shell (header, tab nav, `#content`, and two modals for add/delete). `renderer.js` is a single IIFE holding all app logic and state. `style.css` is the styling.

### State and data flow

The renderer keeps the whole app state in one in-memory `state = { dozenten: [] }` object. The canonical pattern for any mutation is: **mutate `state` → call `persist()` → call `render()`**. `persist()` pushes the full state through `dashboardAPI.saveData`; there is no partial/diff saving. `render()` rebuilds the DOM from scratch (`renderTabs()` + `renderPanel()`), so there is no incremental DOM updating — always drive the UI by changing `state` and re-rendering, never by hand-editing the DOM.

Each *Dozent* object is `{ id, name, todos, openProjects, doneProjects, chat }`. List items are `{ id, text, done }`; chat messages are `{ id, text, time }`. IDs come from the local `uid()` helper (timestamp + random). `MAX_DOZENTEN = 4` caps the number of instructors.

`init()` loads persisted data and back-fills `chat: []` on older records that predate that field — follow this pattern when adding new fields to the *Dozent* shape so existing saved files keep loading.

## Conventions

- User-facing strings, list labels, and comments are in German. Match the existing language when touching the UI.
- Build DOM with `createElement` and set user-controlled text via `textContent` (never `innerHTML`) — this is done consistently to avoid injecting untrusted list/chat content.

## Releases (CI)

`.github/workflows/build-release.yml` builds and publishes installers for Windows, macOS, and Linux. It triggers on pushing a `v*` tag (e.g. `v1.0.0`) or manually via **Actions → Build & Release Desktop App → Run workflow**, running `npm run dist -- --publish always` to upload artifacts to GitHub Releases (`publish: github` in `package.json`).

`it-schulung/` has its own, separate release workflow, `.github/workflows/it-schulung-release.yml`, using a distinct tag prefix (`it-schulung-v*`, e.g. `it-schulung-v1.0.0`) so it never collides with the Dozenten Dashboard's `v*` tags in the same repo. Unlike the Dozenten Dashboard workflow, it does not rely on electron-builder's own GitHub publish step (which always computes the release tag from `package.json`'s `version` and would produce the same `v*`-style tag as the root app); instead each OS build uploads its installer as a plain workflow artifact, and a separate `release` job (gated on the `it-schulung-v*` tag) downloads all three and publishes them together to one GitHub Release under the exact pushed tag via `gh release create`.

`fotonetz/` follows the same pattern as `it-schulung/`: its own workflow, `.github/workflows/fotonetz-release.yml`, triggered by a `fotonetz-v*` tag (e.g. `fotonetz-v1.0.0`), building on all three OSes, uploading each installer as a plain workflow artifact, and a `release` job (gated on the `fotonetz-v*` tag) that downloads them and publishes one GitHub Release via `gh release create`.

`pharmatech-app/` follows the same pattern again: `.github/workflows/pharmatech-release.yml`, tag prefix `pharmatech-v*` (e.g. `pharmatech-v1.0.0`), gated on that tag or a manual `workflow_dispatch`, artifact-upload-then-`gh release create`.

`pharmatech-mobile/` has its own workflow, `.github/workflows/pharmatech-mobile-release.yml`, gated on a `pharmatech-mobile-v*` tag or manual dispatch (platform + EAS profile as inputs). It installs the `eas-cli` via `expo/expo-github-action` and kicks off a non-blocking (`--no-wait`) EAS cloud build — this requires an `EXPO_TOKEN` repository secret (an access token from a real Expo account); without it the workflow fails at the EAS login step by design, since EAS builds run on Expo's infrastructure, not the GitHub runner.
