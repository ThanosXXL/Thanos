# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Dozenten Dashboard is a cross-platform Electron desktop app for managing up to four *Dozenten* (instructors). Each instructor owns three lists — a To-Do list (`todos`), open projects (`openProjects`), and completed projects (`doneProjects`) — plus a chat/notes log (`chat`). Projects move between the open and completed lists; all state persists locally as JSON. The UI is in German.

This repository also hosts a second, unrelated project: `omniroute/` is a vendored snapshot of [OmniRoute](https://github.com/diegosouzapw/OmniRoute) (an AI gateway/router, Next.js + TypeScript monorepo), included as-is with its own `package.json`, tooling, and `CLAUDE.md`. It does not share dependencies, build config, or CI with the Dozenten Dashboard — the root `npm install`/`npm start`/`npm run dist` commands above only ever touch the Dozenten Dashboard files (`main.js`, `preload.js`, `renderer/`); nothing in `omniroute/` is packaged into its installers. Treat `omniroute/` as its own project — see `omniroute/CLAUDE.md` and `omniroute/VENDORED.md` for details and provenance. It is a one-time snapshot, not a live sync with upstream.

A third project, `it-schulung/`, is a separate Electron desktop app for managing up to four IT-Schulungen (IT training courses), built with the same architecture as the Dozenten Dashboard (main/preload/renderer split, `contextIsolation: true`, JSON persistence in `app.getPath('userData')`) but as fully independent code: its own `package.json`, `main.js`, `preload.js`, `renderer/`, and data file (`it-schulung-data.json`, separate from `dozenten-data.json`). Each *Schulung* object is `{ id, name, erklaerung, admin, link, todos, offeneThemen, abgeschlosseneThemen, teilnehmer, chat }` — the training-course equivalent of a *Dozent*. `erklaerung` is a free-text description, `admin` names the person responsible, and `link` is the join URL for the daily live session (opened via `shell.openExternal` through an `open-external` IPC handler, restricted to `http(s)` URLs). `teilnehmer` is a fourth list (alongside `todos`, `offeneThemen`, `abgeschlosseneThemen`) holding the course's participants as `{ id, text }` entries. Run it with `npm install` / `npm start` / `npm run dist` from inside `it-schulung/`, not from the repo root. It shares no dependencies, build config, or CI with the Dozenten Dashboard or with `omniroute/`.

A fourth project, `videowelt/`, is a separate Electron desktop app — a black/gold video editor ("VideoWelt") with a gold 3D-glossy camera logo, unrelated in domain to the other three apps but following the same Electron main/preload/renderer split with `contextIsolation: true`. Unlike the other apps it does real media processing: it bundles ffmpeg/ffprobe (`ffmpeg-static`, `ffprobe-static`, driven via `fluent-ffmpeg` from `ffmpeg-export.js`) so users need no separate ffmpeg install. `main.js` handles file-picker dialogs for importing video/audio, probing media metadata, thumbnail generation, running the export pipeline, and project save/load (`.vwproj` JSON files, plus a small `videowelt-settings.json` in `app.getPath('userData')` remembering the last opened project path); `preload.js` exposes this as `window.videoWeltAPI`. The renderer (`renderer/renderer.js`) keeps a persisted `state = { projectName, mediaLibrary, timeline: { videoTrack, audioTrack, textOverlays } }` (saved/loaded via the project file, not auto-persisted like the other apps' `dozenten-data.json`) plus non-persisted UI/playback state; because it is an interactive timeline editor (clip dragging/trimming, dual-`<video>` crossfade preview, requestAnimationFrame-driven playback), it deliberately does **not** follow the other apps' "always rebuild the DOM from scratch" rule — structural changes go through `renderAll()`, but scrubbing and effect sliders update only the affected DOM/video elements directly. Clip effects (brightness/contrast/saturation/grayscale/sepia/blur/rotate/speed/fades) are approximated live in the browser via CSS filters during preview, then re-applied for real in the exported file through an ffmpeg `filter_complex` graph built in `ffmpeg-export.js` (trim/setpts/eq/colorchannelmixer/boxblur/xfade/acrossfade/amix, plus burned-in text overlays rendered through the `ass`/libass filter with a generated ASS subtitle file and a bundled Montserrat font — not `drawtext`, which the bundled static ffmpeg binary does not include). Background-music items on `audioTrack` can carry `loop`/`stretchDuration`: set via the "Auf Videolänge anpassen" button (`fitAudioToVideoLength()` in `renderer.js`), it seamlessly repeats a shorter track to exactly match the video track's total length using ffmpeg's `-stream_loop -1` input option plus an `atrim=duration=<stretchDuration>` cut, rather than the normal single-play `inPoint`/`outPoint` trim; editing `inPoint`/`outPoint` by hand clears `loop` again. `build/samples/demo-musik.mp3` is a bundled sample track (own "🎵 Demo-Musik" button, `import-demo-music` IPC handler) that gets added and auto-fit to the video length in one click; `build/samples/intro-logo.mp4` is the same animated camera-logo splash pre-rendered to an actual video (Playwright + `x11grab` screen capture, not a live CSS re-render — ffmpeg can't play a browser animation), inserted via the "🎬 VideoWelt-Intro einfügen" button / `import-intro-logo` IPC handler at the *start* (`unshift`, not `push`) of `videoTrack`. A selected video clip can be extended into its own follow-up clip via the Clip menu: "Als Schleife wiederholen" (`loopSequence()`) duplicates it in place after itself (repeatable for more loops), "Zeitlupen-Kopie einfügen" (`slowmoSequence()`) does the same at half speed — both produce an ordinary second `videoTrack` entry, individually editable, not a special linked pair. `effects.smoothSlowmo` (checked whenever `speed < 1`) swaps the plain `fps=` filter for ffmpeg's `minterpolate` (motion-compensated frame interpolation) in `buildVideoFilterChain()`, trading render time for judder-free slow motion. The per-clip color/transform filter logic is split into two reusable builders in `ffmpeg-export.js`, `buildTransformFilterParts()` (flip/rotate) and `buildColorFilterParts()` (eq/sepia/blur/hue/sharpen/vignette) — same order as before this split (transform → scale/pad → fps/minterpolate → color) inside `buildVideoFilterChain()`, and reused as-is (no scale/pad, full source resolution) by `extractStillFrame()`, which backs the "📷 Standbild exportieren" action (`export-frame` IPC) that grabs the exact preview frame at the playhead, with that clip's effects baked in, as a lossless PNG. Text overlays carry a `fontFamily` (`'Montserrat'` or `'Open Sans'`, the bundled humanist-sans alternative under `build/fonts/`); it drives both the live CSS preview and an ASS `\fn` override per line in `buildAssSubtitleFile()`. The header is a real dropdown menu bar (Datei/Bearbeiten/Einfügen/Clip/Effekte/Ansicht/Hilfe, `#menubar` in `index.html`, opened/closed via `toggleMenu()`/`closeAllMenus()` and dispatched through the single `dispatchAction(action)` switch in `renderer.js` — every `data-action` button, in the menu or elsewhere, routes through it) plus a full undo/redo history (`pushHistory()`/`undo()`/`redo()`, JSON-snapshotting `{state, selection}` onto `undoStack`/`redoStack`; called once per discrete edit — batched to a single push per drag/slider/typing gesture via a local `historyPushed` flag reset on the gesture's end event, never per intermediate `input` tick). `clip.transitionOut.type` is no longer a closed `none`/`crossfade`/`fadeblack` enum: it's `'none'` or any ffmpeg `xfade` transition name (see `TRANSITION_GROUPS` in `renderer.js` and the mirrored `XFADE_NAMES` allowlist in `ffmpeg-export.js`'s `transitionName()`, which also aliases the old `'crossfade'` value to `'fade'` for projects saved before this). Because `main.js`/`ffmpeg-export.js` spawn ffmpeg/ffprobe as real OS processes and read the font/sample directories from disk, paths under `app.asar` are unusable once packaged (only Electron's own patched `fs`/`require` can see inside the archive, not `child_process` or an external tool) — `ffmpeg-export.js`'s `unpackAsarPath()` rewrites `.../app.asar/...` to the `asarUnpack`-generated `.../app.asar.unpacked/...` mirror for the ffmpeg/ffprobe binary paths, `FONTS_DIR`, and `SAMPLES_DIR`; keep any new bundled runtime asset (fonts, samples, similar) listed in both `build.files` and `build.asarUnpack` in `package.json` and routed through `unpackAsarPath()` the same way. Run it with `npm install` / `npm start` / `npm run dist` from inside `videowelt/`, not from the repo root. It shares no dependencies, build config, or CI with the Dozenten Dashboard, `omniroute/`, or `it-schulung/`.

A fifth project, `videowelt-mobile/`, is VideoWelt's Android/iOS counterpart — a from-scratch Expo/React Native + TypeScript app, not a port of the Electron code (Electron cannot run on mobile). It shares the black/gold theme and the same mental model (import media → build a timeline of clips → trim/speed/effects → text overlays → export) but has its own state shape (`src/state/types.ts`'s `ProjectState`/`Clip`/`MediaItem`/`TextOverlay`, persisted as `.vwmproj` JSON and autosaved to `AsyncStorage`, **not** compatible with the desktop app's `.vwproj`) and its own export engine (`src/export/ffmpegExport.ts`, driven by `ffmpeg-kit-react-native` instead of `ffmpeg-static`/`fluent-ffmpeg`). The app is a five-tab shell (`App.tsx`: Medien/Timeline/Text/Export/Projekt, hand-rolled tab bar, no navigation library) built around a single `ProjectProvider` React context (`src/state/ProjectStore.tsx`) that mutates-then-persists on every change, mirroring the desktop app's `persist()` pattern. Because `ffmpeg-kit-react-native` is a native module, it can never run inside Expo Go — `isNativeExportAvailable()` in `ffmpegExport.ts` detects this at runtime so Medien/Timeline/Text/Projekt stay fully usable there, while the Export tab surfaces a clear message that a dev-client/standalone build is needed. The default `ffmpeg-kit-react-native` npm package ships ffmpeg's "min" flavor (no `drawtext`, no `libx264`); an Expo config plugin (`plugins/withFfmpegKitFull.js`) patches `android/build.gradle` (`ext.ffmpegKitPackage = "full-gpl"`) and the iOS `Podfile` (the `full-gpl` subspec) at `expo prebuild`/`eas build` time so those native projects never need manual edits. `eas.json` defines `development`/`preview`/`production` build profiles (`preview` produces a directly-installable Android APK) for building via Expo's cloud (`eas build`) with the user's own free Expo account — this repo's sandbox has no Xcode, no Android SDK/emulator, and no proxy access to `dl.google.com`/Maven, so real device builds cannot be produced or tested here; what *was* verified here is that `npx tsc --noEmit` is clean, `npx expo export --platform android` and `--platform ios` both bundle successfully via Metro, and `expo prebuild` produces the correctly-patched `android/build.gradle`. Run it with `npm install` / `npx expo start` (Expo Go, no build) or `eas build -p android --profile preview` (real APK) from inside `videowelt-mobile/`, not from the repo root. It shares no dependencies, build config, or CI with the Dozenten Dashboard, `omniroute/`, `it-schulung/`, or `videowelt/`.

## Commands

```bash
npm install     # install dependencies
npm start        # run the app in development (electron .)
npm run dist     # build installers into dist/ via electron-builder (win: nsis, mac: dmg, linux: AppImage)
```

There is no test suite, linter, or build/transpile step — the renderer is plain HTML/CSS/vanilla JS loaded directly, and the main process is plain Node. Changes are verified by running `npm start`.

## Architecture

Standard Electron three-process split with `contextIsolation: true` and `nodeIntegration: false`:

- **`main.js`** (main process) — creates the `BrowserWindow`, and owns all persistence. Registers two IPC handlers, `load-data` and `save-data`, that read/write a single JSON file at `app.getPath('userData')/dozenten-data.json`. `loadData()` returns `{ dozenten: [] }` on any read/parse failure, so a missing or corrupt file degrades gracefully.
- **`preload.js`** — the only bridge. Exposes `window.dashboardAPI` with `loadData()` and `saveData(data)`, each forwarding to `ipcRenderer.invoke`. Any new main↔renderer capability must be added here; the renderer has no direct Node/Electron access.
- **`renderer/`** — the entire UI. `index.html` is the static shell (header, tab nav, `#content`, and two modals for add/delete). `renderer.js` is a single IIFE holding all app logic and state. `style.css` is the styling.

### State and data flow

The renderer keeps the whole app state in one in-memory `state = { dozenten: [] }` object. The canonical pattern for any mutation is: **mutate `state` → call `persist()` → call `render()`**. `persist()` pushes the full state through `dashboardAPI.saveData`; there is no partial/diff saving. `render()` rebuilds the DOM from scratch (`renderTabs()` + `renderPanel()`), so there is no incremental DOM updating — always drive the UI by changing `state` and re-rendering, never by hand-editing the DOM.

Each *Dozent* object is `{ id, name, todos, openProjects, doneProjects, chat }`. List items are `{ id, text, done }`; chat messages are `{ id, text, time }`. IDs come from the local `uid()` helper (timestamp + random). `MAX_DOZENTEN = 4` caps the number of instructors.

`init()` loads persisted data and back-fills `chat: []` on older records that predate that field — follow this pattern when adding new fields to the *Dozent* shape so existing saved files keep loading.

## Conventions

- User-facing strings, list labels, and comments are in German. Match the existing language when touching the UI.
- Build DOM with `createElement` and set user-controlled text via `textContent` (never `innerHTML`) — this is done consistently to avoid injecting untrusted list/chat content.

## Releases (CI)

`.github/workflows/build-release.yml` builds and publishes installers for Windows, macOS, and Linux. It triggers on pushing a `v*` tag (e.g. `v1.0.0`) or manually via **Actions → Build & Release Desktop App → Run workflow**, running `npm run dist -- --publish always` to upload artifacts to GitHub Releases (`publish: github` in `package.json`).

`it-schulung/` has its own, separate release workflow, `.github/workflows/it-schulung-release.yml`, using a distinct tag prefix (`it-schulung-v*`, e.g. `it-schulung-v1.0.0`) so it never collides with the Dozenten Dashboard's `v*` tags in the same repo. Unlike the Dozenten Dashboard workflow, it does not rely on electron-builder's own GitHub publish step (which always computes the release tag from `package.json`'s `version` and would produce the same `v*`-style tag as the root app); instead each OS build uploads its installer as a plain workflow artifact, and a separate `release` job (gated on the `it-schulung-v*` tag) downloads all three and publishes them together to one GitHub Release under the exact pushed tag via `gh release create`.

`videowelt/` follows the same pattern as `it-schulung/`: its own workflow `.github/workflows/videowelt-release.yml`, gated on a `videowelt-v*` tag prefix, artifact-upload-then-`gh release create` (no electron-builder GitHub publish step), `working-directory: videowelt`.
